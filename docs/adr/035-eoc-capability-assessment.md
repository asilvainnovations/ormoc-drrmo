# ADR-035: EOC Capability Assessment board — the 154-item OCD/NDRRMC checklist against the IAT B_EOC evidence, validated by the CDRRMO Head (v1.20.0)

Status: Proposed, 14 Nov 2026, by the lead assessor (Alvin M. Silva). For the CDRRMO Head.

## Context

The EOC Capability Assessment Checklist (OCD/NDRRMC TWG, December 2017, adapted from FEMA) is the national tool for judging how capable an Emergency Operations Center actually is: 154 items in 15 sections, from hazard and vulnerability assessment through site selection, building design, physical security, communications and SOPs to training and exercises. The City accomplished the checklist in November 2026 by matching every item to the evidence already scored in the Institutional Assessment Tool v1-7, Part B_EOC (43 indicators in 7 domains): each item maps to the B_EOC indicators that answer it, and the item status derives from the weakest mapped indicator score (3 or 4 = Met, 2 = Partially met, 1 = Largely unmet, 0 = Not met; an item with no mapped indicator carries "No direct IAT indicator"). Until now that answer lived only in a workbook: nothing on the platform showed the EOC's capability against the checklist, kept the evidence and gap text with each item, or tracked which SOP, protocol, workflow or form closes each gap.

## Decision

1. **Three tables** (migration `20261114003000_eoc_assessment.sql`): `eoc_assessment_items` (the 154 checklist items, with `section`, `section_sort`, `item_no`, `item_text`, primary/alternate EOC applicability and `iat_links` — the B_EOC indicator ids the item maps to), `eoc_assessment_runs` (one run per assessment round; `draft` until the CDRRMO Head validates it, then locked), and `eoc_assessment_responses` (one row per run and item: `status`, `evidence`, `gap`, `recommended_action`, and `tool_links` — a JSON array of `{code,title}` display links to the SOP, Protocol, Workflow or Form records that close the gap, the same controlled vocabulary as the Manual). `v_eoc_assessment_board` denormalizes runs × items × responses for the board.
2. **The derivation rule lives in SQL** (`app.eoc_assessment_status(integer[])`, ADR-005): the weakest mapped score decides; NA scores are ignored; no mapped score means `no_direct_indicator`. `src/domain/eoc_assessment.ts` mirrors it, and `src/domain/eoc_assessment.test.ts` keeps the two in parity (plus exhaustive small arrays and the seeded distribution). The status is stored on the response — it is the workbook's answer at seed time and the assessor's answer afterwards; the function is the rule both must agree with, and scoring itself stays in Assess.
3. **Reads offline, edits and validation online.** Items are reference data: any active user reads everything from the local store (ADR-003). Recording or editing a response (evidence, gap, recommended action, tool links) belongs to the assessment team — assessor, validator, EOC Manager, EOC staff, CDRRMO Head, admin — enforced by RLS and `app.guard_eoc_assessment` with plain-word refusals (errcode 42501), like `app.guard_raci`. Validating a run is an authority action (ADR-006) for the CDRRMO Head or admin only; the guard stamps `validated_by`/`validated_at`, and a validated run and its responses are locked (approved records are immutable — a new run opens the next round). Responses are corrected, never removed. Every row carries `version`; the client sends the version it saw and a stale write surfaces as SQLSTATE PT409 (never 40001), handled by `updateOnline` with the platform's conflict message.
4. **Capability board screen** (`src/features/eoc-assessment/`, route `/eoc-assessment`). The 154 items grouped by the 15 sections (collapsible), each item a row with a status chip — Met green, Partially met amber, Largely unmet orange (new `--accent-soft` token, kept clear of the reserved RACI and EOC alert colours), Not met red, No direct IAT indicator grey — summary counts in the header, an item drawer for evidence / gap / recommended action and tool links (editable only while the run is a draft and the user holds a write role), and a "Validate run" action shown and enabled only for the CDRRMO Head and admin. A dashboard card on Today links in, and the EOC board links across. The board links out to DDRiVE (`/eoc/risk`) and states the boundary: DDRiVE stays the risk-intelligence source; this module links out and never re-scores risk.
5. **Seeded from the accomplished workbook, never invented.** `scripts/eoc_assessment_seed.py` reads the accomplished checklist workbook at generation time (the workbook is never copied into the repo) and emits `supabase/seed/parts/38_eoc_assessment.sql`: the 154 items verbatim, one baseline run `IAT v1-7 (Oct 2026)` — always a draft, seeds never mark content validated or approved — and the 154 responses with the workbook's status, evidence, gap and recommended action verbatim. Before writing, the generator cross-checks every mapped indicator id and the workbook status against the IAT B_EOC scores (weakest-score derivation); a contradiction stops the generator. Ids are deterministic uuid5 in the platform namespace; everything is insert-only, so a re-run neither duplicates rows nor resets the assessment team's edits. The all-"Not assessed" alternate-EOC column is carried faithfully: `applies_alternate` is false for every seeded row because no alternate EOC is designated yet (IAT B2.7, score 0).

## Consequences

- The board is a display and maintenance layer over evidence scored elsewhere: it never changes IAT scores, and the status of an item changes through Assess, not through the drawer.
- Every edit and the validation are audited (`app.track` → `app.audit`) and optimistic-concurrency protected.
- A new assessment round is a new run (insert by the assessment team, e.g. after the next IAT); old validated runs stay readable as the record. Runs and responses are never deleted by clients.
- The `--accent-soft` token is reserved for the "largely unmet" severity step; other screens do not reuse the orange chip for decoration.
